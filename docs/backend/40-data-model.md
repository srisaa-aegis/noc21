# 4. Database Model (PostgreSQL 16 / Drizzle ORM) — Revision 2

> Specification only. The Drizzle schema modules and the SQL migrations are produced in
> Phase B1.

## 4.0 Principles and conventions

1. **Every table's primary key is `id integer GENERATED BY DEFAULT AS IDENTITY`** (R2-2).
   This applies to reference tables (including fire stations, roles, statuses and
   application types), configuration, engine tables and junction tables. **The only
   exception is `files.id uuid`** (uploaded files).
2. **Natural codes are unique columns, never keys**: `application_types.code = 'P'`,
   `build_types.code = 'res'`, `wf_definitions.code = 'P-MSB'`, `directions.code = 'N'`, and
   so on.
3. **Reference rows whose legacy id is already an integer keep that value as their `id`**
   (districts 1–13, statuses 1–9, dept roles 1–10, equipments 1–13, fire stations). They are
   seeded with `OVERRIDING SYSTEM VALUE`, and the identity sequence is then moved past the
   maximum. This keeps every legacy reference valid. For example, a workflow task
   `role_id: 6` still means DFO.
4. **Parent-local counters** that the frontend uses (`block_id`, `floor_id`, `doc_id`,
   `task_id`, `fileid`, `step_id`, `sl_no` …) are stored as **`*_no` columns**
   (`block_no`, `floor_no`, `doc_no`, …) with `UNIQUE (parent_id, *_no)`. The serialiser maps
   `blocks.block_no → "block_id"` on the wire. In SQL, `*_id` always means a foreign key to
   some `id`, which removes the ambiguity.
5. **Foreign keys are named `<referenced_singular>_id`**: `application_id`, `block_id`,
   `district_id`, `fire_station_id`, `role_id`, `user_id`.
6. **Normalise what is queried, reported, joined or authorised on. Use JSONB for immutable
   snapshots and opaque or grid payloads**: rule definitions, workflow definition versions,
   task form data, revision snapshots and the FFE cell grid (§4.7).
7. Money is `numeric(14,2)`; areas and heights are `numeric(12,3)`; timestamps are
   `timestamptz` (UTC); business dates are `date` (Asia/Kolkata).
8. Soft delete uses `deleted_at`. Audit and workflow events are append-only. Optimistic
   locking uses `row_version`.
9. Integer capacity check at 100 000 applications/year (§4.13): the largest table grows by
   about 4 M rows/year, against a 2.1 billion limit. `integer` is safe for centuries, so no
   table needs `bigint`.

### Data correction: fire station `"4Q"` (R2-2)

`"4Q"` (Kunavaram, East Godavari / district 4) is the only non-numeric station id. It appears
in `fire-stations.json`, in the legacy `NOC-base/apis/FireStations.txt`, and in one officer's
`stations[]` in `users.json`. The seed applies a **recorded correction**.
`backend/seed/corrections.json` maps `{ "fire_station": { "4Q": 199 } }`, where 199 is the
next free id after the current maximum of 198. The correction is applied to the station and
to every reference to it, and is logged by the seeder. The final id is open question N-1.

### Statuses (Q-63)

| id | name | category | is_system | notes |
|---|---|---|---|---|
| 1 | Draft | draft | ✔ | fixed |
| 2 | Submitted | submitted | ✔ | fixed |
| 3 | Inspected | in_process | — | configurable |
| 4 | Reviewed (ADFS) | in_process | — | configurable |
| 5 | Reviewed (DFS-CD) | in_process | — | configurable |
| 6 | Pending Final Approval | in_process | — | configurable; `is_pre_decision = true` |
| 7 | Approved / Issued | approved | ✔ | fixed |
| 8 | Returned with Comments | returned | ✔ | fixed |
| 9 | Rejected | rejected | ✔ | fixed |

Rules, enforced by a trigger plus the service layer:

- System rows cannot be deleted and cannot change `id` or `category`.
- New statuses can only be added in the `in_process` category, with ids starting at 10.
- Exactly one active `in_process` status has `is_pre_decision = true`.
- Ordering uses `sort_order`, never `id`.

Code never refers to 3–6. The workflow validator checks that stage statuses are
`in_process`, that they do not go backwards in `sort_order`, and that the stage before the
decision sets the `is_pre_decision` status. Reports use `category`. The frontend colours
badges by `category`.

These tables **replace** Revision 1's `rule_trees`, `fee_configs`/`fee_rates`,

- Approval level and renewal period are **decision tables**.

  **decision trees**, kept verbatim.

Every calculation result records the version ids it used (§4.8), so an auditor can always see
*which* rules produced a fee or an approval level.

**Why FFE cells moved to JSONB (R2-7).** At 100 000 applications/year a normalised cell
table grows by about 26 M rows/year. The grid is always read and written whole per block,
and the server recomputes it on every save, which would cause heavy write amplification.
One row per equipment item holds about 2.6 M rows/year. The three summary columns keep the
questions inspectors and reports actually ask ("where is provided < required?") indexable.
A CHECK with `jsonb_typeof` validates the cell shape, and the Zod schema validates it in the
API.

(§4.13).

|---|---|
| `files` | **`id uuid`** PK, `storage_backend`, `bucket` (the filesystem driver uses the logical bucket `noc`), `storage_key` uq, `original_name`, `mime_type`, `size_bytes bigint`, `checksum_sha256`, `uploaded_by` fk users, `created_at`, `deleted_at`, `scan_status`, `scan_at` |

Storage key scheme (S3-compliant, sharded for 100 000 applications/year):

```
applications/{shard}/{application_id}/documents/{file_uuid}.pdf
applications/{shard}/{application_id}/requested/{file_uuid}.pdf
applications/{shard}/{application_id}/dept/{file_uuid}.{pdf|jpg|png}
applications/{shard}/{application_id}/decision/{file_uuid}.pdf
applications/{shard}/{application_id}/blocks/{block_no}/plans/{file_uuid}.pdf
shard = zero-padded floor(application_id / 1000), e.g. 000123
```

Keys contain no user-supplied text. The original file name is kept only in the database.

## 4.11 Integrity rules in the database

1. At most one live workflow instance per subject (partial unique index).
2. Application numbers are unique, and drafts have none.
3. Statuses: system rows are protected, and exactly one `is_pre_decision` row (trigger).
4. Published rule-set versions and definition versions are immutable (trigger).
5. Revisions, `wf_events` and `audit_log` are append-only (trigger).
6. Rating is between 1 and 5; SLA days are between 1 and 365; amounts are ≥ 0.
7. Deletes cascade inside the aggregate and are restricted towards reference and
   configuration data.

## 4.12 Application numbering at 100 000/year

The legacy format is `yyyymm` + 4 digits, which allows 9 999 per month. At 100 000 per year
the average is 8 333 per month, so **busy months will overflow**. Proposed design
(follow-up N-2):

- `yyyymm` + **5 digits** (`20250700001`, 11 characters) for all new numbers. The column is
  `varchar(12)` and the 10-character seed numbers remain valid.
- Numbers come from `application_number_sequence`:
  `INSERT … ON CONFLICT (prefix) DO UPDATE SET last_seq = last_seq + 1 RETURNING last_seq`,
  inside the submit transaction. The number is gap-free for committed submissions.

## 4.13 Sizing (100 000 applications/year, 100 concurrent users)

| Table | Rows / year (est.) | 10-year |
|---|---|---|
| applications | 100 k | 1 M |
| blocks | 200 k | 2 M |
| block_floors | 2 M | 20 M |
| block_ffe_items | 2.6 M | 26 M |
| other block children (sides, ospaces, escapes, …) | ~3 M combined | 30 M |
| wf_tasks | 1.2 M | 12 M |
| wf_events | 2 M | 20 M |
| process_log | 1.5 M | 15 M |
| application_documents / files | 2.5 M | 25 M |
| application_revisions | 230 k (~7 GB) | 2.3 M |
| audit_log | ~4 M | 40 M |

Database size is roughly 25–40 GB/year including indexes. That is a single PostgreSQL
instance with no sharding.

- **Partitioning:** `audit_log`, `wf_events` and `application_revisions` are designed to be
  range-partitioned by year when they pass about 50 M rows. The partition key is added to the
  primary key at that point. It is not needed at go-live.
- **Indexes:** BRIN on the time columns of append-only tables.
- **Connections:** 100 concurrent users need a pool of 20. No PgBouncer is needed at this
  scale.
- **File volume** (from N-8): about 2.5 M files/year. At an estimated 1.5 MB average this is
  about **3.75 TB/year** on the storage root, which dominates capacity and backup planning.
  Hence the sharded keys.

## 4.14 Migration and change tracking

| Concern | Approach |
|---|---|
| Generate | `drizzle-kit generate` → `backend/src/db/migrations/NNNN_*.sql` + meta journal |
| Apply | `db:migrate`, transactional, under `pg_advisory_lock`; recorded in `drizzle.__drizzle_migrations` |
| Triggers / views / partial indexes not expressible in the schema DSL | custom SQL migrations (`drizzle-kit generate --custom`), reviewed like any other |
| Drift | `drizzle-kit check` + an `information_schema` comparison test in CI |
| Data migrations | `migrations/data/NNNN_*.ts`, recorded in `seed_state` |
| Rules / workflow changes | **not migrations**: new published versions in `re_rule_set_versions` / `wf_definition_versions`, audited in `config_change_log` |
| Destructive changes | expand → backfill → contract across releases; `pg_dump` before deploy |
| Legacy database | none exists (Q-6) — no import tooling |
