# Phase B1 — Delivery Notes

**Status: delivered and running.** The portal now runs against a real
PostgreSQL backend for everything it reads. Writes arrive in phases B2 and B3.

---

## 1. What was built

### 1.1 Monorepo and libraries

```
noc/
├── packages/rules-engine/      @srisaa/rules-engine    — generic, reusable
├── packages/noc-domain/        @srisaa/noc-domain      — NOC rules on top of it
├── backend/                    @srisaa/noc-api         — Fastify + Drizzle + PostgreSQL
├── frontend/                   the Angular 21 portal (now talking to the API)
├── e2e/smoke.mjs               browser smoke test (Playwright / Chromium)
└── scripts/smoke.sh            API smoke test on a scratch database
```

**`@srisaa/rules-engine`** (no NOC knowledge, no runtime dependencies, browser-safe):

- **decision trees** — the legacy `uploads/rules/*.rule` format, evaluated verbatim;
- **decision tables** — ordered rows, operators (`in`, `between`, `ge`, `isTrue`, …), hit
  policies (`FIRST`, `PRIORITY`, `COLLECT`) and aggregation across a collection
  (`MAX_RANK`, `MIN`, `MAX`, `SUM`, `LIST`) — which is how "the highest approval level of
  all blocks" and "the shortest renewal period of all blocks" are expressed as data;
- **parameter sets** — versioned constants (fees, escape limits);
- structural **validation** (cycles, unreachable nodes, unknown operators, reserved fact
  names), **explain traces**, stored **regression cases**, and a `RuleSetSource` port.
- **Conformance proof:** all 16 shipped trees are evaluated over 1 638 fact combinations
  and must match the browser's current evaluator exactly.

**`@srisaa/noc-domain`** — the NBC/G.O.Ms.No.119 calculations, the FFE grid, fees, approval
level, renewal period, submission validation, certificate facts and the read-only workflow
views, re-expressed on the rules engine. The portal's existing 128 domain tests run against
it unchanged. `assess()` is the single entry point the server uses to recompute everything.

### 1.2 Database

- **79 tables**, every one keyed by `id integer` (identity) — `files.id uuid` is the only
  exception, as instructed. Natural codes (`'P'`, `'res'`, `'P-MSB'`) are unique columns.
- Reference rows keep their legacy integer ids (districts 1–13, statuses 1–9, roles 1–10,
  equipment 1–13, fire stations), so every historical reference stays valid.
- Generic engine storage: `re_*` (rule sets and immutable published versions) and `wf_*`
  (definitions, versions, instances, tasks, events, SLA, escalations) — no NOC columns, so
  another application can reuse them.
- The application aggregate, its blocks and children, revisions (Q-39), assessments,
  payments with the **frozen fee** (Q-57), documents, and the audit/outbox/job tables.
- **Triggers** enforce what code must not be trusted with: append-only audit/events/
  revisions, immutable published rule and workflow versions, the status guard (N-4), and the
  cache-version bump with `NOTIFY`.
- **4 views** (`v_application_summary`, `v_current_tasks`, `v_active_tasks`, `v_report_base`).
- Migrations: `0000_initial.sql` (generated by drizzle-kit) + `0001_platform.sql` (triggers,
  views, checks, generated search column), applied under an advisory lock.

### 1.3 Seed

`npm run db:seed` loads, in one transaction: all master data, the 20 rule sets (12 FFE trees
+ 4 auxiliary trees + approval-level and renewal tables + fee and escape parameters), the 12
workflow definitions with their SLA and bindings, the 9 forms, the 22 demo accounts
(argon2id) and the 14 demo applications with their 11 workflow runs. It is idempotent
(master data is upserted, demo data replaced) and records a checksum of its inputs.

**Data correction (N-1):** the fire station `"4Q"` (Kunavaram) is **dropped** from the master
list and from the officer (`rfo.officer`) who referenced it. The seeder prints both
corrections on every run, and `backend/seed/corrections.json` records the decision.

### 1.4 API (`/api/v1`)

| Area | Endpoints |
|---|---|
| Auth | login · refresh (rotating, reuse-detecting) · logout · me · register · forgot-password · reset-password · change password |
| Caching | `/meta/versions` · `/bundles/:b` (ETag) · `/bundles/:b/v/:n` (immutable) · `/bootstrap` |
| Reference | the 20 catalogue lookups + the 5 rule-tree routes + `/rules/sets*` |
| Config | fees, approval-level rules, renewal rules, workflows, forms, SLA, statuses (reads) |
| Applications | list (scopes mine/dept/all, filters, pagination) · aggregate · summary · **assessment** · validation · process log · revisions · certificate facts |
| Admin | accounts, audit, officers |
| Files | metadata · one-time download token · token download (streams; an S3 driver would redirect here) |
| Portal transition surface | `/portal/applications`, `/portal/accounts`, `/portal/escalations` — whole-collection shapes so the existing Angular services work unchanged until B2/B3 refactors them |
| Ops | `/health` · `/ready` · `/version` |

Writes answer **501** with a sentence naming the phase that delivers them.

Everything is problem+json on failure, with `detail` carrying the portal's own wording
(*"Invalid username or password."*, *"This account has been deactivated…"*).

### 1.5 Caching (the strategy from `55-caching.md`, working end to end)

PostgreSQL triggers bump `cache_versions` and `NOTIFY` → each API process rebuilds that
bundle in memory (pre-serialised, brotli + gzip) → every response carries
`X-Data-Versions` → the browser stores bundles in IndexedDB and refetches only what moved.

Measured on the running system: **reference 66 KB → 10.7 KB brotli, rules 200 KB → 4.4 KB,
content 60 KB → 7.7 KB**; a returning browser makes **zero** reference-data requests; an
external `psql` UPDATE is visible to the API in well under a second.

### 1.6 Storage

`StorageProvider` port + `FilesystemStorage` rooted outside the web root (the config layer
refuses a root inside `frontend/`). S3-compliant by construction: flat sharded keys
(`applications/000123/123456/documents/<uuid>.pdf`), opaque bytes, atomic writes, metadata
only in the database, downloads through `createDownload()`. A contract test suite is written
against the **port**, so the future S3 driver must pass the same 9 tests. No S3 code.

### 1.7 Frontend integration

- `environment.apiMode` (`http` default, `mock` for the fixture build), `proxy.conf.json`.
- `http-routes.ts` — the one file that maps each catalogue entry to a REST route.
- `HttpBackend` + `ApiError` (server `detail` becomes `Error.message`, field issues kept).
- `authInterceptor` (bearer + cookie + **single-flight silent refresh and replay**),
  `dataVersionInterceptor`.
- `SessionStore` — the access token lives **in memory only**.
- `AuthService` on the real API, with the session restored from the refresh cookie at start.
- `ReferenceDataStore` — IndexedDB cache, version-driven refresh, BroadcastChannel across
  tabs, private bundles dropped on logout; `LookupService` now reads bundles instead of
  issuing ~25 requests.
- All 389 existing tests still pass (plus 7 new ones for the HTTP layer).

## 2. Deviations from the plan (and why)

| # | Deviation | Reason |
|---|---|---|
| D-B1-1 | The domain code was **copied** into `@srisaa/noc-domain` rather than moved out of the frontend; the frontend still uses its own copy for live calculation. | Keeps the 389 frontend tests and the wizard untouched while the write paths are still mock-based. The move happens in B2, when the wizard switches to the server's assessment. Behaviour parity is enforced by the 128 package tests + the conformance suite. |
| D-B1-2 | A **transition surface** (`/portal/*`) returns whole collections. | The portal's feature services were written against the fixture collections. The proper resource API (`/applications?scope=…`, paginated) is built and tested; the services move onto it in B2/B3, and `/portal/*` is then deleted. |
| D-B1-3 | Our database environment variables are `DB_HOST`/`DB_PORT`/… not `PGHOST`/`PGPORT`. | This sandbox exports `PGHOST=/tmp`; libqq picks those up and silently overrode the project settings. |
| D-B1-4 | `legacy-peer-deps=true` in `.npmrc`. | npm 10's peer resolver crashes on vitest's optional `jsdom`/`canvas` peers inside a workspace root. |
| D-B1-5 | `frontend/` is not an npm workspace; it keeps its own `node_modules`. | Same npm bug; the root scripts call it with `npm --prefix frontend`. |
| D-B1-6 | The workflow **engine** package is not built yet (only its storage tables and the read-only views in `@srisaa/noc-domain`). | It belongs to B2, where the transitions land. |

Highlights worth knowing about:

- **Fixture parity** — every one of the 14 demo applications is read back out of PostgreSQL
  and compared field-by-field with `applications.json`; only the documented differences
  (`row_version`, empty-collection normalisation) are allowed.
- **Cache invalidation** — a direct `UPDATE` in `psql` must reach the API and the lookup
  response; a rolled-back transaction must not bump anything.
- **Schema invariants** — a test walks `information_schema` and fails if any table's primary
  key is not a single integer `id` (except `files`).

## 4. What is explicitly not in this build

Creating or saving an application, uploading a file, paying, submitting, any workflow
transition, any administrative write, reports computed on the server, and escalations. They
return **501** with the phase named in the message. The Angular app is fully usable for every
read-only journey; `npm run start:mock` still gives the complete fixture-based demo.
